## Reglas de comportamiento (todas las IAs: Claude Code · opencode · Antigravity)

Estas reglas aplican a Claude Code, opencode y Antigravity por igual, en todos los proyectos:

1. **Resumen de cierre y Firma de Telemetría Dinámica** — (a) Terminar toda sesión que toque código/configs con un resumen + lista COMPLETA de archivos modificados. (b) En cada respuesta sustancial o acción de desarrollo, incluir al pie el badge de telemetría visible:
   - Si la respuesta fue procesada directamente por la IA en sesión:  
     `> 🤖 **IA:** <Nombre> | **Modelo:** <Modelo> | **Esfuerzo:** <Low/Medium/High/Off> | **Cuota Restante:** Gemini: <XX>% · Claude: <YY>%`
   - Si la tarea fue despachada en background a Claude CLI:  
     `> 🤖 **Orquestador:** Antigravity | **Motor:** Claude Code CLI (Sonnet) | **Esfuerzo:** <Esfuerzo> | **Cuota Restante:** Gemini: <XX>% · Claude: <YY>%`  
   **Prohibido asumir valores estáticos a ciegas:** el badge DEBE reportar con fidelidad matemática el nivel de esfuerzo real y activo fijado por Haward en la interfaz, y quién fue el motor real de cómputo.
2. **Circuito de cierre ordenado** — al finalizar: (1) actualizar `CLAUDE.md` del repo si hay paths/reglas nuevas → (2) actualizar notas del vault → (3) **`git push` del vault PRIMERO** → (4) `git push` del proyecto. El vault se pushea antes porque los agentes remotos (AUTO, ODI, etc.) lo leen al arrancar. Está implementado en `/github`.
3. **Notas del vault vía herramienta de Obsidian** — todo `.md` del vault se crea/edita respetando las convenciones de [[00 - Meta/Guía de Uso]] (en Claude y Antigravity: skill `obsidian-markdown`; en opencode: comando `/crear-nota`). No escribir Markdown del vault a mano sin respetar frontmatter y wikilinks.
4. **Cambios visuales con cuidado de diseño** — ante cualquier cambio de UI, aplicar criterio de diseño (en Claude: skills `frontend-design`, y `mobile-app-ui-design` si el alcance es ≤768px / touch / responsive).
5. **Commits en español**, descriptivos.
6. **Documentar decisiones como ADR exhaustivo** inmediatamente, en `02 - Decisiones/` del vault. Un ADR no es un resumen de 3 líneas: debe incluir contexto y problema de negocio, alternativas evaluadas con matriz de decisión de criterios (KISS, seguridad/secretos OCI, SLA), decisión técnica, diagrama o flujo de ejecución, inventario de recursos/tablas/schemas afectados (sin secretos), lecciones aprendidas / trampas superadas (`[!bug]`), y trade-offs con **Análisis Pre-Mortem preventivo** ante cambios críticos en Producción (puntos de fallo probables, salvaguarda y plan de rollback). Es la base de conocimiento forense del equipo.
7. **Actualizar Infra.md** al descubrir un OCID, IP, ruta o referencia a secreto nueva — antes del commit final.
8. **PR vs push directo** — repos propios y cambios chicos: push directo a `main` (`/github`). Repos **colaborativos** (otra persona también hace push; hoy ninguno, Journal pasó a ser propio el 2026-11-04) o features grandes/riesgosas: branch + **Pull Request** (`/pr`, usa `gh pr create`).
9. **Context7 proactivo (docs actualizadas)** — antes de escribir o depurar código con librerías/SDKs externas (sobre todo de versión reciente o que cambian rápido: EF Core, Microsoft Graph, Azure SDK, React, etc.), consultá **Context7** (`use context7` / tools `mcp__context7__*`) para confirmar la API vigente. No asumas APIs de memoria. La IA decide cuándo aplica (no hace falta para librería estándar trivial).
10. **Trabajá en el repo correcto (no en el orquestador)** — el workspace multi-root arranca con el `cwd` en `D:\Proyectos\CoreOps` (carpeta principal). Antes de escribir `WORK_SESSION.md`, `TASKS.md`, `docs/` o código, confirmá que tu working dir es el repo del proyecto (`D:\Proyectos\Github\<PROYECTO>`), NO CoreOps. Nunca dejar archivos de un proyecto dentro de `CoreOps\`.
11. **No crear GitHub Actions por defecto** — no generar `.github/workflows/` al scaffoldear un proyecto nuevo ni "para tener CI/CD". Se puede usar si el usuario lo pide explícitamente para ese repo puntual, pero no es parte del scaffold estándar.
12. **Informe de cierre e ingesta en NotebookLM y Auto-Recovery de Sesión** — (a) **Informe:** al terminar un proyecto/pedido (no en cada sesión), `/generar-informe` produce un `.docx` replicable con la skill `docx` en `docs/informes/YYYY-MM-DD-titulo.docx` a nivel repo (o `projects/<ID>/docs/` → `resueltos/<ID>/docs/` en tickets de DataOps). (b) **Ingesta — nunca a mano con `nlm source add`:** el único camino es el script canónico `python D:/Proyectos/CoreOps/scripts/sync_notebooklm.py`, idempotente, que sube lo que falta a los cuadernos `bago` (corporativo) y `personal` en las DOS cuentas (`default` = `htillero@gmail.com`, `bago_corp` = `htillero@bago.com.ar`, ver [[00 - Meta/NotebookLM]]). Qué sube: el `README.md` de cada `resueltos/<caso>/` (la ficha del caso, regla 19; título `<caso>.md`) y los `docs/informes/*.docx` de cada repo; escanea secretos antes de subir (regla 17) y bloquea el archivo si encuentra uno. Lo corren `/generar-informe` (paso 5) y `/cierre` (paso 5): **un caso movido a `resueltos/`, un README de caso resuelto editado o un informe nuevo NO está cerrado hasta correrlo.** Un README ya subido que cambió se detecta (hash registrado) y se reemplaza solo, sin duplicar la fuente. Control: `sync_notebooklm.py --status` muestra por caso y perfil si está SUBIDO, CAMBIADO, FALTA o BLOQUEADO (`--verify` lo compara con el contenido real guardado en NotebookLM); los casos de `projects/` se ven como ACTIVO y solo se suben con `--include-active`. (c) **Auto-Recovery de sesión, en este orden y sin pedirle nada al usuario hasta agotarlo:** 1) `nlm auth refresh --profile <perfil> --http-only`; 2) `nlm auth refresh --profile <perfil>` (navegador oculto de Edge, `auth.browser = edge`); el script ya los prueba solo. Prohibido pedirle al usuario que corra un login sin haber agotado ambos. (d) **Escalamiento obligatorio:** si ambos fallan (el script termina con código `3` y lo dice), la IA se detiene, avisa a Haward con claridad que no pudo autenticarse sola y le da el comando exacto: `nlm login --profile <perfil> --clear --storage protected` (el `--clear` es necesario: sin él `nlm` solo valida las credenciales vigentes y no recrea el perfil del navegador). No se da la ingesta por hecha. `sync-agents.ps1 -Check` avisa cuando la sesión de `nlm` está vencida.
13. **README.md profesional, nunca placeholder** — el `README.md` raíz de cualquier repo es la primera impresión en GitHub. Debe seguir obligatoriamente el diseño profesional (estándar `odi-traceability-app`): incluir Badges, Emojis en las secciones (`🎯 Objetivos`, `🏗 Arquitectura`, `🚀 Instalación`, `📁 Estructura`, `🔄 Roadmap`), y un **diagrama Mermaid** obligatorio si hay un flujo, pipeline o arquitectura que se explique mejor visualmente. Si al alinear (`/alinear`) un proyecto existente su README es débil o "simple", recrearlo en la misma sesión bajo este estándar, no dejarlo pendiente. **Regla de preservación (obligatoria):** al crear o recrear un README existente, CONSERVAR todo su contenido específico — advertencias de seguridad, convenciones, inventarios de archivos/scripts, tablas, comandos y contexto operativo — reestructurando y embelleciendo, **nunca** reemplazándolo por texto genérico de plantilla. Antes de guardar, comparar con el anterior (`git diff`) y verificar que no se perdió información; si no se puede conservar, no tocarlo y avisar. Nunca regenerar READMEs en lote sin revisar cada diff.

(e) No correr `graphify hook install` ni los `graphify <ia> install` "always-on" (escriben hooks/reglas propios en el repo y pisarían `.githooks`) sin pedirlo; instalar solo el paquete oficial `graphifyy` (doble "y").
16. **Sincronización del circuito — OBLIGATORIA al manejar proyectos** — cada vez que se crea, renombra, mueve, archiva o incorpora un repo, o se cambia el contrato (bloque compartido de `AGENTS.md`), los comandos (`_prompts-sistema-hibrido.md`) o los MCP/skills globales: (1) editar solo la fuente canónica (`Scripts/AGENTS.md` o el vault); (2) correr `Scripts/.claude/commands/sync-agents.ps1` y `Scripts/scripts/sync-prompts.ps1`; (3) verificar con `sync-agents.ps1 -Check`: debe terminar SIN `DRIFT`, `SIN HOOK`, `HOOK DESACTUALIZADO` ni `FUERA DEL CIRCUITO` (repo nuevo → `-Onboard`); (4) commit + push del archivo propagado en CADA repo (vault primero; repos colaborativos por PR); (5) reflejarlo en cada IA: Antigravity → `~/.gemini/GEMINI.md`, opencode → `opencode.json`/`AGENTS.md`, Claude Code → `CLAUDE.md`/skills. Un cambio de proyecto NO está cerrado sin este paso: forma parte del circuito de cierre (regla 2), no es opcional ni "para después".
17. **Secretos: nunca en archivos versionados** — ni contraseñas, tokens, API keys, claves privadas (tampoco en base64), wallets de Oracle (`cwallet.sso`, `ewallet.p12`, `Wallet_*.zip`) ni sentencias como `ALTER USER ... IDENTIFIED BY '...'`; y tampoco en docs, notas del vault, informes, notebooks (`.sqlnb`) ni borradores. Usar OCI Vault / variables de entorno / Credential Manager; en la documentación poner solo el nombre u OCID del secreto. Las credenciales propias de las IAs (`~/.claude.json`, `~/.gemini/`) nunca se copian a un repo. Todo repo debe tener activo el hook `pre-commit` canónico (`Scripts/.githooks/pre-commit`, bloquea el commit de verdad) y `sync-agents.ps1 -Check` lo verifica; prohibido saltearlo con `--no-verify`. Si aparece un secreto: **no commitearlo, avisar al usuario SIN reproducir el valor y recomendar rotarlo** — si ya llegó a git, la rotación es obligatoria aunque se borre el archivo.
18. **Simplicidad y no sobre-ingeniería (KISS / YAGNI — Senior Dev)** — Las IAs deben evitar la tendencia a sobre-estructurar, crear wrappers artificiales o inventar código innecesario. Ante cualquier requerimiento: (1) ¿Es realmente necesario escribir código nuevo? (2) Reutilizar utilidades y funciones existentes en el repo antes de crear nuevas. (3) Preferir cmdlets/módulos estándar nativos (PowerShell nativo, Python standard library, OCI CLI) antes de importar librerías externas o frameworks pesados. (4) Implementar la solución más directa y limpia que funcione. Aplicar refactorización KISS (`/code-simplifier`) para desenredar lógica anidada y eliminar código muerto; tolerancia cero a fallos silenciosos (`/silent-hunter`): prohibido catch vacíos, excepciones tragadas o fallbacks que oculten caídas reales en pipelines. *Nota: La simplicidad aplica al volumen de código; la seguridad, manejo de errores (try/catch), idempotencia y documentación forense siguen siendo obligatorias.*
19. **Gestión homogénea de SQL y Scripts en proyectos (Doble rol, Literate README & Causa Raíz)** — En repositorios operativos (DataOps, etc.), las soluciones técnicas se organizan con separación estricta y documentación autosuficiente: (a) El archivo ejecutable suelto (`consulta.sql`, `aplicar.py`, `run.ps1`) guarda el código limpio que dio con la solución definitiva para ejecución directa en DB o terminal (prohibido guardar sentencias intermedias fallidas o scratchpads). (b) El `README.md` del caso actúa como informe técnico autosuficiente y fuente única de verdad para el equipo y NotebookLM: detalla el ticket, solicitante, contexto, justificación, **análisis de causa raíz (5 Porqués / Ishikawa)** ante incidentes o bugs para explicar el origen real del fallo, **bloques de código íntegros embebidos con sintaxis resaltada** (` ```sql `, ` ```python `) y evidencia de validación (sanitizado sin contraseñas según regla 17). Para cambios de esquema en bases de datos (ADW/RDS), aplicar metodología Expand-Contract sin downtime (`/database-migrations`), evaluación de radio de impacto previo (`/change-impact`) con linaje de dependencias (`/data-lineage`), bloque de validación (`DRY RUN` o conteo de registros) y script/bloque de Rollback independiente de los datos. Los casos activos viven en `projects/<ID-nombre>/` y al resolverse se mueven a `resueltos/<ID-nombre>/`. Los notebooks `.sqlnb` son consolas locales de historial personal y nunca se versionan en Git.
20. **Protocolo de Memoria en 4 Niveles y Ahorro de Tokens (Tiered Memory)** — Para evitar pérdida de memoria inter-sesión e inter-IA y erradicar la saturación de contexto (*Lost in the Middle*), las 3 IAs operan en 4 fases estrictas: (1) **Triage:** Al iniciar un caso, consultar `WORK_SESSION.md` + `00 - Meta/Infra.md` (coordenadas) + `00 - Meta/Operaciones.md` (querys/scripts canónicos) vía `mcpvault`. Prohibido reinventar consultas SQL de diagnóstico o comandos de infraestructura ya probados. (2) **Grounding Forense:** Ante problemas complejos, fallas de OCI/ADW o dudas de arquitectura, consultar primero a NotebookLM (`nlm query notebook bago "..."`) vía MCP; la nube procesa las 99 fuentes sin inflar el contexto local (solo ~250 tokens in/out). Si falla autenticación, aplicar auto-recovery en segundo plano de inmediato. (3) **Ejecución KISS:** En el repo del proyecto, escribir código limpio ejecutable y README literate autosuficiente (regla 19); ante pipelines lentos o movimientos masivos, aislar cuellos de botella y verificar prueba de coherencia (`/data-throughput`). (4) **Doble Cierre:** Si hubo decisión de diseño → ADR en `02 - Decisiones/` (regla 6); si hubo nuevo script/query recurrente → `Operaciones.md`; si se completó el caso/informe → ingestar en NotebookLM (regla 12); y push ordenado (vault primero, regla 2).
21. **Gráficos: elegir el tipo según la pregunta** — al crear o cambiar cualquier gráfico (dashboards, informes, notebooks, apps, artefactos), leer [[00 - Meta/Reglas de Gráficos]] en el vault, decidir qué pregunta responde (comparar → barras; evolución → líneas; partes de un total → sectores/donut con pocas partes; distribución → histograma/caja/violín; relación → dispersión; flujos → Sankey; causas → Pareto; tareas → Gantt) y explicar la elección en una línea. Reglas fijas: **barras desde cero**, **sin 3D en los datos**, **correlación ≠ causalidad**, datos de ejemplo marcados como ilustrativos. En Claude, sumar la skill `dataviz`.
22. **Orquestador Inteligente y Conciencia de Cuotas (Omni-Repo Smart Dispatcher)** — Para operar sin costo de API Keys por token, las consultas y tareas se rutean considerando su complejidad técnica y el estado de cuotas de las suscripciones planas (Claude Team Plan, Antigravity Google Pro, NotebookLM Tier 2 y OpenCode Free). 23. **Prohibido asumir sin investigar (Verificación de Hechos y Límites Técnicos)** — Tolerancia cero a inventar, extrapolar o asumir limitaciones técnicas, cuantitativas o de funcionalidad (cuotas, tamaños máximos, límites de archivos de herramientas como Quick Share, restricciones de protocolos, cuellos de botella de red, APIs, bases de datos o sistemas operativos) basándose en memoria no verificada o suposiciones. Antes de afirmar que algo "no se puede", "no lo soporta" o "está limitado a X", la IA debe obligatoriamente investigar y contrastar la información mediante búsqueda web (`search_web`), documentación oficial (`context7` o docs del fabricante) o validación empírica en el entorno. Si tras la búsqueda persiste una duda o la documentación es ambigua, la IA debe manifestarlo con honestidad técnica ("no hay un límite documentado formalmente; probemos con una muestra piloto") en lugar de crear fricción, dudas o bloqueos infundados al usuario.
24. **Telemetría de Consumo, Pacing Semanal y Balanceo Multi-Tanque (Agentic FinOps)** — El uso de modelos en Antigravity y Claude se gobierna por datos empíricos de consumo, no por suposiciones. (a) **Telemetría continua:** Cada sesión registra sus tokens y ritmo de quema en `Scripts/scripts/quota_telemetry.py` (ejecutado en `/cierre`), actualizando el dashboard vivo en `00 - Meta/Telemetria-Cuotas.md`. (b) **Pacing Semanal ($\Delta_{\text{pacing}}$):** La cuota semanal de Gemini es un techo rígido; el semáforo compara el porcentaje restante de cuota contra el porcentaje de tiempo restante para el reseteo. Si $\Delta_{\text{pacing}} < -5\%$, se activa la preservación de Gemini para tareas de alto valor, desviando procesos batch o refactors masivos hacia **Claude Code CLI** (Tanque 3) o **NotebookLM**, o hacia **OpenCode Free** (Tanque 4) para utilitarios sin costo. (c) **Preservación del Orquestador (Shock de 5 horas):** Antigravity es la consola central. Si su ventana de 5 horas cae por debajo del 30%, Antigravity no realiza escaneos masivos ni generación kilométrica de código directamente: actúa como torre de control delegando la fuerza bruta a Claude CLI vía `/despachar` o comando de fondo para no asfixiar el puesto de mando. (d) **Alerta Proactiva de Esfuerzo en Chat:** Dado que el usuario opera por defecto en esfuerzo Low (o Medium) para máxima agilidad (~2s), ante requerimientos de alta complejidad analítica o riesgo de producción (ADW, DDL, deadlocks), la IA debe emitir una alerta proactiva sugiriendo elevar el selector a Medium o High (o Sonnet Thinking), dejando la decisión en manos del usuario sin imponer demoras de razonamiento inesperadas.
